# ComplyOn LLC — Marketing Site

The single-page marketing site for ComplyOn LLC, an independent compliance
and risk advisory practice. It is a React 18 app built with Vite, using the same entry-point and
component structure as CompressQuick/frontend-web. Production builds are
static files. Inquiry delivery uses a separate small Node.js/Express API in
`server/`.

## Requirements

- Node.js 20.19+ (developed on v22)
- npm

## Getting started

```bash
npm install
npm --prefix server install
npm run dev
```

The dev server prints a local URL (http://localhost:3001, set in
`vite.config.js`) and reloads the page whenever you save.

In another terminal, run `npm run server:dev` to start the inquiry API on
port 3002. The local `server/.env` contains the AWS email settings copied
from shouldertocryon-server; this file is ignored by Git. For a fresh clone,
copy `server/.env.example` to `server/.env` and supply the server credentials.

## Scripts

| Command | What it does |
| --- | --- |
| `npm run dev` | Start the Vite dev server with React Fast Refresh. |
| `npm run build` | Build a static site into `dist/`. |
| `npm run preview` | Serve the built `dist/` locally to check it before deploying. |
| `npm run server` | Start the inquiry API on port 3002. |
| `npm run server:dev` | Start the inquiry API with Node's file watcher. |

## Layout

```
index.html          HTML shell, metadata, structured data and font preloads
src/main.jsx        React entry point
src/App.jsx         page composition
src/components/     header, footer and one component per page section
src/hooks/          inquiry form state and scroll/reveal effects
src/index.css       original stylesheet and all responsive breakpoints
src/assets/         founder portrait and self-hosted font subsets
server/             standalone Express API, SES delivery and API tests
server/validation.js pure field validation shared with the React form
server/.env         private AWS/server settings (git-ignored, never deploy publicly)
vite.config.js      React plugin, dev server and build output settings
dist/               build output (generated, git-ignored)
```

Edit the components in `src/components/` for page content and `src/index.css`
for styles. Edit `index.html` for metadata and structured data. Everything in
`dist/` is regenerated by `npm run build`; do not edit generated files.

## How the page is organised

`src/App.jsx` renders the header, hero, stats, about, quote band, services,
who we serve, track record, engagements, FAQ, contact, and footer in the
original order. Components keep the original HTML structure and content,
with only the syntax changes needed for JSX. The original CSS lives in
`src/index.css`, grouped by the same section comments.

The menu and inquiry form use React state and event handlers. The existing
scroll tracking and reveal animations live in `src/hooks/usePageEffects.js`,
with listener, animation-frame, and observer cleanup for unmounts and hot
reloads. The FAQ still uses native `<details>` elements.

The favicon is an inline SVG data URI in the head — there is no icon file.

## Fonts

Newsreader (the serif) and Inter (the sans) are **self-hosted** from
`src/assets/fonts/`. The page makes no third-party request to render, which removes a
render-blocking round trip to `fonts.googleapis.com` and avoids sending
visitor IP addresses to Google — the practice German courts have found to
breach GDPR.

The files come from the `@fontsource*` packages, kept as devDependencies so
the origin is traceable and updates are a reinstall away. The committed `.woff2` files in `src/assets/fonts/` are referenced by the
stylesheet and font preloads. Vite includes them in the production build.

Newsreader is the **variable** font with an optical-size axis (`opsz`
6–72), the same version the original design loaded from Google Fonts.
Browsers apply `font-optical-sizing: auto` by default, so large text such as
the hero headline gets the high-contrast display cut and small text gets the
sturdier text cut. (The static `@fontsource/newsreader` files are fixed at
the 16pt cut, which makes the big headings look heavier and blunter.)
`src/assets/fonts/newsreader-latin-opsz-200-700.woff2` (~128 kB) is
`@fontsource-variable/newsreader/files/newsreader-latin-opsz-normal.woff2`
with its weight axis trimmed to 200–700, the range the stylesheet uses:

```bash
python -c "from fontTools.ttLib import TTFont; from fontTools.varLib.instancer import instantiateVariableFont as i; f=i(TTFont('node_modules/@fontsource-variable/newsreader/files/newsreader-latin-opsz-normal.woff2'), {'wght': (200, 400, 700)}); f.flavor='woff2'; f.save('src/assets/fonts/newsreader-latin-opsz-200-700.woff2')"
```

Inter ships as static 300/400/500 files (latin subset, woff2). To add an
Inter weight: copy the matching file out of `node_modules/@fontsource/inter/
files/`, then add an `@font-face` rule in the stylesheet. To use a Newsreader
weight above 700, rebuild the variable file with a wider `wght` range.

The Newsreader file and Inter 400 (body text) are preloaded in the head; the
rest load from the `@font-face` rules. All declare `font-display: swap`, so
text paints immediately in the fallback face rather than staying invisible.

Newsreader's `$` has two vertical strokes. The stats band (`.stat-num`)
uses a single-stroke `$` instead: `src/assets/fonts/source-serif-4-dollar-400.woff2`
is Source Serif 4 (SIL OFL) subset to that one glyph (under 1 kB), loaded
as the `Stat Dollar` family with `unicode-range: U+0024`, so every other
character still falls through to Newsreader. To rebuild it, run
`pyftsubset` (from fonttools) on
`@fontsource/source-serif-4/files/source-serif-4-latin-400-normal.woff2`
with `--unicodes=U+0024 --flavor=woff2`.

## Responsive design

The base CSS is the desktop layout; every media query is a `max-width`
override that adapts it downward. Type and spacing are fluid (`clamp()`), so
the breakpoints only have to handle the column counts — each grid drops a
column at the width where its narrowest cell stops reading well, rather than
all of them at one shared number:

| Breakpoint | What changes |
| --- | --- |
| 1100px | Services go from three columns to two |
| 1000px | Engagements go to two columns; the third card spans the row |
| 980px | Hero body, about, section headers and contact stack; stats go to two columns; expertise grid halves |
| 900px | The nav collapses into the menu button |
| 720px | Services, stats and engagements go to one column; client rows and track-record entries stack; the form's name fields stack |
| 460px | Hero buttons go full width; the expertise grid goes to one column |
| 360px | The tagline under the wordmark is dropped |

Anchor offsets come from one variable: `--nav-h` (86px, 74px below 900px).
The sticky header height, the top of the mobile menu panel and the
`scroll-margin-top` that keeps a jumped-to section clear of the header all
read from it, so changing the header height is a one-line change.

### The header

The nav carries six destinations, which stop fitting beside the wordmark at
around 900px. Below that the links collapse into a drop-down panel opened by
the menu button; the panel closes on link click, on Escape, and on a resize
back to the desktop layout.

The collapsed styles are gated behind a `js` class on `<html>`, added by
the page effect after React mounts. As with the reference React project,
JavaScript is required to render the app.

## Motion and depth

Two custom properties carry the whole motion system: `--ease` (one curve) and
`--settle` / `--quick` (one slow duration for arrivals, one fast one for
hovers). Nothing animates on a timing the rest of the page does not already
use, and only `opacity` and `transform` are animated, so none of it can shift
the layout — Lighthouse still reports a cumulative layout shift of 0.

Everything arrives the same way — fade up 14px — and one IntersectionObserver
watches every element individually. What changes is the company an element
keeps: items that cross into view in the same batch are ordered by row and
then left to right, and the `--i` custom property the script sets on each one
staggers them 80ms apart, capped at five steps. A three-across grid therefore
ripples left to right, while the same grid stacked on a phone arrives one card
at a time as each is reached — which is the point of watching items rather
than their container, since a phone-height grid would otherwise play its whole
sequence off screen. The hero uses the same mechanism but fires on load, as it
is already in view.

Both are gated behind the `js` class on `<html>`. The reduced-motion block
resets the starting transforms and disables transitions, and the effect
reveals all items immediately when reduced motion is requested.

Hover effects live in one `@media (hover: hover) and (pointer: fine)` block.
On a touch screen `:hover` latches after a tap, which would otherwise leave a
service card lit and a button raised until the next tap landed somewhere else;
touch gets `:active` press states instead, and the tap highlight is suppressed.
Phones also override the shadow tokens with tighter spreads — a 44px blur that
reads as depth on a desktop reads as haze on a 390px screen — and the footer
links get thumb-sized padding. Both gutters use `max(var(--gutter),
env(safe-area-inset-*))`, so a notched phone in landscape keeps its margins.

Shadows are tokens too — `--shadow-soft`, `--shadow-lift`, `--shadow-btn`,
`--shadow-nav` — all wide, soft and nearly colourless. The page is flat by
design; these lift a surface a millimetre off the paper rather than floating
it. They appear on the sticky header once the page has scrolled (`.nav.stuck`,
toggled from a passive scroll listener), on a hovered service card, on the
contact panel, and under the buttons and the portrait.

A second observer follows the reader: whichever section sits in a band a
fifth of the way down the viewport marks its nav link `.active`, which keeps
that link's underline drawn and sets `aria-current`. Engagements has no nav
link, so when the band comes up empty the previous link is held rather than
blinking off; it clears only when the reader is back above the first section.
On phones the panel marks the current section with a tinted row and a purple
rule in the gutter rather than an underline, since the stacked links already
carry dividers. The panel's rows pay for that marker rule with left padding
and the Contact button pays with margin, so both land on the page gutter. The
toggle's two bars slide to the centre line and turn 45° into a cross, driven
off the `aria-expanded` attribute the menu script already maintains — the
state the button announces and the state it draws cannot drift apart.

The remaining detail work is CSS-only: the rule above each section label draws
itself in, nav and footer links grow an underline from the left, the focused
form field thickens its rule, an FAQ answer fades up as it opens, the portrait
warms out of greyscale and scales 3% inside a clipping frame, and the quote
band carries an oversized quotation mark at 9% white.

## Deployment

Run:

```bash
npm run build
npm run preview
```

`npm run build` produces a self-contained `dist/` directory. Upload the
**contents of `dist/`** to any static host when you are ready to deploy.
The inquiry API must run separately in Node.js. Do not deploy the source
`index.html` or `src/` directory directly.

Vite bundles and minifies the JavaScript and CSS and includes the original
portrait and font files. Asset URLs are relative (`base: './'`), so the same
build can be hosted at a domain root or under a subdirectory. Navigation
uses the existing section anchors, so no client-side router or route
fallback configuration is needed.

For the API, deploy the `server/` directory to a Node.js host, securely supply
its `.env` settings, run `npm ci --omit=dev` inside that directory, and start
it with `npm start` (or your process manager). The API allows cross-origin
requests from any website; rate limiting still applies to inquiry submissions.

By default the form calls `/api/inquiry`. Proxy this path on the frontend
domain to the Express server. Vite already proxies it to port 3002 for both
`npm run dev` and `npm run preview`; production hosting needs its own proxy.
If there is exactly one trusted reverse proxy, set `TRUST_PROXY=1` so rate
limiting uses the visitor's IP. Leave it at `0` when accessing Node directly.

For a separately hosted API, set the following in the root `.env.local`
**before** `npm run build`:

```dotenv
VITE_INQUIRY_API_URL=https://api.example.com/api/inquiry
```

The endpoint URL is public configuration. AWS credentials belong only in
the server environment, never in a `VITE_` variable or the static host.

## Contact form

`POST /api/inquiry` receives JSON and sends a branded HTML email with a
plain-text fallback through AWS
SES to **hirethedeveloperkamal@gmail.com**. The recipient is fixed in
`server/email.js`; requests cannot override it. Reply-To contains the
visitor's name and email. The configured sender is
`ComplyOn inquiries <info@shouldertocryon.health>`, reusing the sender address
from shouldertocryon. Set `SES_FROM_EMAIL` to another SES-verified identity
when you want to change it.

The email layout lives in `server/email-template.js`: a purple ComplyOn
header, contact summary, service highlight, full message, and a reply button.
The reply button prefills the visitor's address, the original inquiry subject
with a `Re:` prefix, and a quoted copy of their message and contact details,
leaving space above for your response.
It uses inline styles and presentation tables, with narrower spacing on
phones and no external image or font downloads. Submitted content is HTML
escaped and message line breaks are preserved. Restart the API after editing
the template (`npm run server:dev` restarts automatically).

Required: first name, last name, email, and message. Organization and area
of interest remain optional. The client and API share the same validation:
whitespace trimming, email syntax, field types, control-character rejection,
and length limits (names 100, organization 200, email 254, area 100, message
5000 characters). The API also retains the honeypot, limits JSON requests to
32 KB, and permits five requests per IP per 15 minutes. The limiter uses
in-memory storage for this single-process mini server.

Only an accepted SES request returns success. Provider failures return a
generic error and let the visitor retry; credentials and message contents
are not logged. Automated tests mock SES and do not send real email.

Email composition uses Nodemailer's [stream transport](https://nodemailer.com/transports/stream)
to produce MIME bytes, then AWS `SendRawEmailCommand`, matching the reference
server's delivery API. Keep the same AWS region as the sender identity. If
the AWS account is in the SES sandbox, the destination must also be verified.

## Lighthouse CI

`npm run lighthouse` builds the site and runs Lighthouse against `dist/`
three times, reporting the median. Configuration is in `lighthouserc.json`;
HTML and JSON reports land in `.lighthouseci/` (git-ignored) — open the
`.report.html` file for the full breakdown.

Historical scores for the original HTML version (mobile form factor;
rerun the audit to measure the React build):

| Category | Score |
| --- | --- |
| Performance | 100 |
| Accessibility | 100 |
| Best Practices | 100 |
| SEO | 100 |

The thresholds in `lighthouserc.json` are retained to catch regressions.

### Known issues the audit reports

1. **`modern-image-formats` / `uses-responsive-images`** — the founder photo
   is a 936×1245 JPEG displayed at roughly a third of that. A WebP or AVIF
   at display size saves about 85 kB.
2. **`unminified-css`** — retained as a warning; Vite now minifies the
   extracted stylesheet during the build.

Both are set to `warn`, so they appear in the output without failing the
run.
